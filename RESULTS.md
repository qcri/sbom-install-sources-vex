# One library, seven installs: SBOM → scanner → VEX

**Question.** The same PyYAML 5.3.1 code (CVE-2020-14343) is installed in different ways. Does the SBOM identify it correctly, does the scanner flag it correctly, and does a correct supplier VEX statement get applied?

**Run it:** `python3 -I run.py` (stages: `fetch build evidence sbom vex scan report probe`). Raw scan output from the run reported here: `out/scans-2026-10-08.tar.xz`. Tool versions are in `out/versions.txt`: Syft 1.54.1, Grype 0.120.1 (DB built 2026-10-08), Trivy 0.75.0 (DB 2026-10-07), vexctl v0.4.4. Re-scanning every committed SBOM on 2026-10-13 with newer DBs gave the same 32 results; the probes in §4 are from that date.

## Terms

| term | meaning here |
|---|---|
| SBOM generator | Syft, or Trivy as `trivy image --format cyclonedx`. Writes the SBOM of an image. |
| scanner | Grype, or Trivy as `trivy sbom`. Reads an SBOM, matches its components against vulnerability data, and applies VEX with `--vex`. |
| Syft→Grype | SBOM generated by Syft, scanned by Grype. Likewise Syft→Trivy, Trivy→Grype, Trivy→Trivy. |
| finding | one vulnerability ID reported on one component (PURL). |
| oracle | the ground truth of §1: is the PyYAML in the image exploitable? |
| verdict | does a scan report CVE-2020-14343 at all, compared with the oracle: ✅ agrees, ❌ FP reported but not vulnerable, ❌ FN vulnerable but not reported. |
| suppressed | taken out of a scan's results by `--vex`, because an applicable statement says `fixed` or `not_affected`. Grype lists these under `ignoredMatches`; Trivy shows them with `--show-suppressed`. |
| post-filter | `vexctl filter`: removes results from a scanner's SARIF output after the scan, using a VEX document. |

## Setup

One image per variant (`variants/<name>/Containerfile`). All images are `ubuntu:20.04` (pinned by digest) with Python 3.8.10, and they all contain the same `app/app.py`, which calls `yaml.full_load` on client data. Open any of them with `podman run -it vexlab/<name>:1.0 bash`.

| variant | how PyYAML is installed |
|---|---|
| deb-unpatched | `apt install python3-yaml=5.3.1-1` (original 20.04 release) |
| deb-patched | `apt install python3-yaml=5.3.1-1ubuntu0.1` (Ubuntu security update) |
| pypi | venv, `pip install PyYAML==5.3.1` (sdist from PyPI, built in the image) |
| git | venv, `pip install git+https://github.com/yaml/pyyaml.git@5.3.1` |
| local | venv, `pip install ./pyyaml-5.3.1` (unmodified sdist tree, sha256-checked by `fetch`) |
| local-backport | venv, same tree plus **Ubuntu's own `CVE-2020-14343.patch`**, version set to `5.3.1+acme1` (see below) |
| pypi-fixed | venv, `pip install PyYAML==6.0.2` (control) |

**local-backport** models an organisation ("Acme") that cannot upgrade PyYAML and instead *backports* the fix: it takes the change that fixed the CVE in a newer release (upstream commit 7adc0db, released in 5.4) and applies it to the 5.3.1 it ships, as Linux distributions do. `fetch` applies the patch Ubuntu used (`src/patches/CVE-2020-14343.patch`, byte-identical to Ubuntu's and the same change as 7adc0db) to the unmodified 5.3.1 tree and sets the version to `5.3.1+acme1`. In PEP 440, `+acme1` is a *local version label*: it marks a rebuild without changing the public version. So `5.3.1+acme1` still falls in the advisory's affected range `< 5.4`, while its PURL, `pkg:pypi/pyyaml@5.3.1%2Bacme1`, differs from upstream's `pkg:pypi/pyyaml@5.3.1`. This is the case VEX exists for: the code is fixed, but a scanner that only sees the version still reports the CVE (§3). The distinct version is what lets the supplier's statement name this rebuild without also covering upstream 5.3.1 (§4.5).

The pip-built 5.3.1 variants have no libyaml C extension (`with_libyaml: false` in the evidence); the debs and the 6.0.2 wheel have one. This does not affect the CVE: `full_load` uses the pure-Python `FullLoader`.

## 1. Ground truth (`out/<variant>/evidence.txt`)

`app/oracle.py` runs the public PoC with a harmless payload (`eval("6*7")`). A result of `(42,)` means exploitable.

| variant | metadata version | dpkg version | `constructor.py` sha256 | PoC | truth |
|---|---|---|---|---|---|
| deb-unpatched | 5.3.1 (egg-info) | 5.3.1-1 | `3b751a7f…` | `(42,)` | **vulnerable** |
| deb-patched | **5.3.1** (egg-info) | 5.3.1-1ubuntu0.1 | `90d8247d…` | ConstructorError | not vulnerable |
| pypi | 5.3.1 | – | `3b751a7f…` | `(42,)` | **vulnerable** |
| git | 5.3.1 (`direct_url.json`: commit 538b5c9) | – | `3b751a7f…` | `(42,)` | **vulnerable** |
| local | 5.3.1 (`direct_url.json`: `file:///src/pyyaml`) | – | `3b751a7f…` | `(42,)` | **vulnerable** |
| local-backport | 5.3.1+acme1 (`yaml.__version__` still `5.3.1`) | – | `90d8247d…` | ConstructorError | not vulnerable |
| pypi-fixed | 6.0.2 | – | `90d8247d…` | ConstructorError | not vulnerable |

Integrity checks: pip's `RECORD` matches every installed file, and `dpkg --verify` matches the deb's md5sums. The only `dpkg --verify` warning is `/usr/share/doc/python3-yaml/README`, which the minimal Ubuntu image strips. `RECORD` is written by pip at install time, so it shows only that the files were not changed afterwards; the link to the upstream releases is the hash comparison below.

**There are only two versions of `constructor.py`, the file that contains the vulnerability.** The vulnerable one (`3b751a7f…`) is in the 5.3.1 sdist and in Ubuntu's `5.3.1-1`; the fixed one (`90d8247d…`) is in Ubuntu's `5.3.1-1ubuntu0.1`, in local-backport and in PyYAML 6.0.2. (Other modules still differ between the patched 5.3.1 and 6.0.2.) Yet in deb-patched the Python metadata says `5.3.1`: the fix is visible only in the dpkg version (`-1ubuntu0.1`) and in the file contents. Syft's SBOMs of the two deb images do list `constructor.py` with its SHA-256, but no scanner uses file hashes for matching.

All SBOMs are CycloneDX 1.7 JSON. `out/tables.md` has the full table, including the fields where each component records its deb source package (§4.2) and its install origin (§4.3).

| variant | Syft | Trivy |
|---|---|---|
| deb-* | **two** components: `pkg:deb/ubuntu/python3-yaml@<rev>?…&upstream=pyyaml` **and** `pkg:pypi/pyyaml@5.3.1` | one: `pkg:deb/ubuntu/python3-yaml@<rev>?arch=amd64&distro=ubuntu-20.04` |
| pypi | `pkg:pypi/pyyaml@5.3.1` | `pkg:pypi/pyyaml@5.3.1` |
| git | `pkg:pypi/pyyaml@5.3.1?vcs_url=git+https://github.com/yaml/pyyaml.git@538b5c9…`, plus a `vcs` external reference with the commit | `pkg:pypi/pyyaml@5.3.1` (origin lost) |
| local | `pkg:pypi/pyyaml@5.3.1`, plus a `vcs` external reference `file:///src/pyyaml` | `pkg:pypi/pyyaml@5.3.1` (origin lost) |
| local-backport | `pkg:pypi/pyyaml@5.3.1%2Bacme1`, plus a `vcs` external reference `file:///src/pyyaml` | `pkg:pypi/pyyaml@5.3.1%2Bacme1` (origin lost) |
| pypi-fixed | `pkg:pypi/pyyaml@6.0.2` | `pkg:pypi/pyyaml@6.0.2` |

`<rev>` is the Debian version, `5.3.1-1` or `5.3.1-1ubuntu0.1`. Neither SBOM generator puts a PURL on the SBOM root (the image), because a local image archive has no registry digest.

## 3. Verdicts: does the final scan output match the oracle?

This is the end-to-end result, and it answers questions 2 and 3: does the scanner report the vulnerability correctly, and does a correct VEX statement fix the wrong reports? Each cell is the verdict for one SBOM→scanner pair on one variant, **without VEX / with the supplier VEX applied by `--vex`**. §4 explains every ❌.

The supplier VEX: the author is "Example PSIRT" (`vexctl create`); the status comes from the oracle (`affected` if vulnerable, otherwise `fixed`); the product is the PURL the supplier knows it shipped (from the dpkg version or the wheel metadata); the statement lists both the CVE and the GHSA ID. An `affected` statement removes nothing, so for the four vulnerable variants both verdicts are always the same. Findings behind each verdict: `out/tables.md`; raw results: `out/<variant>/scan/`.

|---|---|---|---|---|
| deb-unpatched (vuln) | ✅ / ✅ | ✅ / ✅ (a) | ❌ FN / ❌ FN (b) | ✅ / ✅ |
| deb-patched (not) | ❌ FP / ❌ FP (c) | ❌ FP / ❌ FP (c) | ✅ / ✅ (d) | ✅ / ✅ |

- (a) Reported only on Syft's PyPI duplicate `pkg:pypi/pyyaml@5.3.1`; Trivy misses the deb component itself (§4.2). Without the duplicate this cell would be an FN.
- (b) Grype cannot link Trivy's `python3-yaml` component to Ubuntu's advisory (§4.2).
- (c) The finding is on Syft's PyPI duplicate. The supplier statement names the deb, so it does not apply to it (§4.1).
- (d) Correct only because Grype cannot match the deb at all, as in (b).

Over the 28 SBOM→scanner pairs, 7 verdicts are wrong without VEX and 3 with `--vex`. The 3 that remain are deb cases, caused by how the SBOMs record a deb (§4.1, §4.2). The 4 that VEX fixed are the backport, which a version-based scanner cannot recognise unless it is told. For local-backport, `fixed` and `not_affected` / `vulnerable_code_not_present` were both applied by both scanners and suppressed the same findings, so the choice between them only matters to the people reading the VEX (§5).

Applying the same VEX documents with `vexctl filter` instead gives 4 wrong verdicts: the FN of Trivy→Grype on deb-unpatched, and three Grype FPs (deb-patched Syft→Grype and both local-backport Grype pairs), because `vexctl filter` never removes Grype's PyPI findings (§4.4). deb-patched Syft→Trivy becomes ✅, but only because `vexctl filter` ignores the product: the deb statement removed a finding on the PyPI component.

## 4. Why the errors happen (`out/probe/probes.txt`, `python3 -I run.py probe`)

Each probe changes one thing (a field in an SBOM, a field in a VEX statement, or the image a statement is applied to) and scans again. The subsections match the sections of `probes.txt`.

### 4.1 One deb install, two SBOM components (Syft, CycloneDX)

**What is in the image.** dpkg installs `python3-yaml 5.3.1-1ubuntu0.1`. Among its files is `/usr/lib/python3/dist-packages/PyYAML-5.3.1.egg-info`: Python packaging metadata, written from PyYAML's own `setup.py` when Debian built the package.

**What Syft records.** Its dpkg cataloger reports the deb, `pkg:deb/ubuntu/python3-yaml@5.3.1-1ubuntu0.1?…`. Its Python cataloger reads the egg-info and reports a second component, `pkg:pypi/pyyaml@5.3.1`.

**Why the second component looks unpatched.** Ubuntu records its fix only in the Debian revision, the `-1ubuntu0.1` after the upstream version. Python metadata has a single `Version` field, which holds the upstream version `5.3.1`, and Ubuntu does not change it when it backports a patch. So nothing in `pkg:pypi/pyyaml@5.3.1` distinguishes these files from the vulnerable 5.3.1 on PyPI.

**Why it becomes a false positive.** A scanner treats a `pkg:pypi` component as a package from PyPI and looks it up in the PyPI advisory, GHSA-8q59-q68h-6hv4, whose affected range is `< 5.4`. `5.3.1` is in that range, so Grype and Trivy both report CVE-2020-14343 on the patched deb's files.

**Why only with CycloneDX.** Syft does know that the second component belongs to the deb. In its own JSON format it records the relationship `python3-yaml` → `pyyaml` as `ownership-by-file-overlap` (in SPDX: `OTHER`, with that comment). Grype uses it: on distros whose feed also lists unfixed vulnerabilities, Ubuntu included, Grype drops a language package that an OS package owns when one version starts with the other, here `5.3.1-1ubuntu0.1` and `5.3.1` (`removePackagesByOverlap`, `grype/pkg/package.go`). CycloneDX `dependencies` only express "depends on", and Syft's CycloneDX output leaves the ownership relationship out, so the reader sees two unrelated components. Probe on the deb-patched image:

| what Grype reads | finding on deb-patched |
|---|---|
| the image itself | none |
| Syft JSON SBOM | none |
| Syft SPDX SBOM | none |
| Syft CycloneDX SBOM (used in §3) | `pkg:pypi/pyyaml@5.3.1` (FP) |

On deb-unpatched the first three give only the deb finding; CycloneDX gives the deb and the duplicate. Trivy as a scanner does not use Syft's relationship: it reports the FP from Syft's SPDX as well as from its CycloneDX. Trivy as an SBOM generator never has the problem, because it skips Python packages whose files belong to an OS package.

**Effect on VEX.** The supplier's deb-patched statement names `pkg:deb/ubuntu/python3-yaml@5.3.1-1ubuntu0.1?arch=amd64&distro=ubuntu-20.04`, so it cannot apply to a finding on `pkg:pypi/pyyaml@5.3.1`. A statement that could, with product `pkg:pypi/pyyaml@5.3.1`, would also apply to every image with the real, vulnerable 5.3.1 (§4.5, probe b).

### 4.2 Deb source package: each scanner reads only its own vendor's fields

**Background.** Debian and Ubuntu build *binary* packages from a *source* package: the binary package `python3-yaml` comes from the source package `pyyaml`. Ubuntu's security data lists CVE-2020-14343 under the source package. A scanner therefore has to know that `python3-yaml` comes from `pyyaml`; looking up `python3-yaml` finds nothing.

Where each SBOM generator records the source package:

| SBOM | field |
|---|---|
| Syft, CycloneDX | PURL qualifier `upstream=pyyaml` and property `syft:metadata:source=pyyaml` |
| Trivy, CycloneDX | property `aquasecurity:trivy:SrcName=pyyaml` (plus `SrcVersion` and `SrcRelease`) |
| Trivy, SPDX | free text: `"sourceInfo": "built package from: pyyaml 5.3.1-1"` |

Probes on deb-unpatched (vulnerable). Each row edits the `python3-yaml` component of one SBOM, scans it, and checks whether the scanner now reports CVE-2020-14343 on that component:

| SBOM | edit to the `python3-yaml` component | scanner | finding on the deb? |
|---|---|---|---|
| Trivy | none | Grype | no (FN) |
| Trivy | append `&upstream=pyyaml` to its PURL | Grype | yes |
| Trivy | add properties `syft:package:metadataType=dpkg-db-entry` and `syft:metadata:source=pyyaml` | Grype | yes |
| Trivy SPDX | none | Grype | no |
| Syft | none | Grype | yes |
| Syft | remove the `upstream` qualifier, keep the property | Grype | yes |
| Syft | remove the `syft:metadata:source` property, keep the qualifier | Grype | yes |
| Syft | remove both | Grype | no |
| Syft | none | Trivy | no (it reports only the PyPI duplicate) |
| Syft | add property `aquasecurity:trivy:SrcName=pyyaml` | Trivy | yes |
| Syft | add `SrcName=pyyaml`, `SrcVersion=5.3.1` and `SrcRelease=1` | Trivy | yes |

So Grype reads the source package from either of Syft's two fields, and Trivy only from its own `SrcName`. Neither reads the other vendor's field, and Grype does not parse Trivy's SPDX text. On a Syft SBOM Trivy also warns: "Third-party SBOM may lead to inaccurate vulnerability detection".

### 4.3 Install origin is not in the PURL

pip records where a package came from in `direct_url.json`: the git URL and commit, or `file:///src/pyyaml`. Syft copies it into CycloneDX `externalReferences` (with type `vcs`, even for a local directory) and, for git only, into the PURL qualifier `vcs_url`. Trivy keeps neither. Scanners and VEX match on the PURL, and there pypi and local (and, in Trivy's SBOM, git) are all `pkg:pypi/pyyaml@5.3.1`. Here that changes no verdict, because the code is the same. It matters when a git or local build differs from the release with the same version: local-backport's fix stays visible only because its version changed.

### 4.4 Applying a VEX statement

How `--vex` works in both scanners: a statement *applies* to a finding when its vulnerability (the name or an alias) equals the finding's ID and its product matches the component's PURL (§4.5 has the exact rules). An applicable `fixed` or `not_affected` statement suppresses the finding.

**Negative control.** Take the deb-patched statement, "`pkg:deb/ubuntu/python3-yaml@5.3.1-1ubuntu0.1?arch=amd64&distro=ubuntu-20.04` is `fixed`", and apply it to the vulnerable pypi image, whose only PyYAML component is `pkg:pypi/pyyaml@5.3.1`. The statement is about a package that is not in this image, so the correct outcome is that nothing changes.

| applied to the pypi image's scan | result |
|---|---|
| `grype --vex` | finding kept: the statement's product matches no component |
| `trivy --vex` | finding kept, same reason |
| `vexctl filter` on Trivy's SARIF | finding **removed** (FN) |
| `vexctl filter` with a statement about an unrelated package, `pkg:npm/left-pad@1.0.0` | finding **removed** (FN) |

`vexctl filter` never compares products. For each SARIF result it takes the rule ID as the vulnerability ID, and if any statement for that ID says `fixed` or `not_affected`, it removes the result (`ApplySingleVEX` in vexctl v0.4.4, `pkg/ctl/implementation.go`). The same thing happens inside the §3 matrix: on deb-patched Syft→Trivy, the deb statement removed the FP on `pkg:pypi/pyyaml@5.3.1`, the right result for the wrong reason.

On Grype's SARIF, vexctl never removes the PyPI findings. Grype names its rules `<vulnerability ID>-<package name>`, here `GHSA-8q59-q68h-6hv4-pyyaml`; vexctl strips that suffix from `CVE-` rule IDs (such as Grype's deb finding, `CVE-2020-14343-python3-yaml`) but not from `GHSA-` ones, so no statement matches. Grype's SARIF does contain the PURL, in the rule properties, but vexctl does not read it.

### 4.5 How `--vex` matches a statement to a finding

**Purpose.** §4.4 shows that `--vex` checks the product. This section measures *how*: which fields must be equal, and how far one statement reaches. That decides whether a correct statement is applied (no misses) and whether it stays in the image it was written for (no leaks).

**Design.** Start from the known-good local-backport statement (product `pkg:pypi/pyyaml@5.3.1%2Bacme1`, vulnerability `CVE-2020-14343` with alias `GHSA-8q59-q68h-6hv4`, status `fixed`). Change one field, then apply the copy to the local-backport SBOM, where `fixed` is true, and to the pypi SBOM, which is vulnerable. Both are Syft SBOMs. "Suppressed" means the statement was applied; "kept" means it was not.

| statement, one field changed | local-backport (`fixed` is true) | pypi (vulnerable) | what it shows |
|---|---|---|---|
| (a) CVE only, no GHSA alias | Grype **kept** (miss), Trivy suppressed | both kept | Grype keys this finding by the GHSA ID and does not use its own CVE link |
| (b) product `pkg:pypi/pyyaml@5.3.1` | both kept | both **suppressed** (leak) | a version in the product must be equal; this statement covers every image with upstream 5.3.1 |
| (c) product `pkg:pypi/pyyaml`, no version | both suppressed | both **suppressed** (leak) | no version means every version |
| (d) GHSA only, no CVE | Grype suppressed, Trivy **kept** (miss) | not run | Trivy keys the finding by the CVE: the mirror image of (a) |
| (e) product with an extra qualifier, `…%2Bacme1?foo=bar` | both kept | not run | a qualifier in the statement must be on the component |

Two more probes on PURL qualifiers:

- (b) applied to the git SBOM, whose PURL is `pkg:pypi/pyyaml@5.3.1?vcs_url=…`: suppressed by both. Qualifiers that only the component has are ignored.
- A `fixed` statement for the deb-unpatched package, with the deb PURL written the way each SBOM generator writes it. Trivy's form (`…?arch=amd64&distro=ubuntu-20.04`) suppresses the deb finding in both Syft→Grype and Trivy→Trivy. Syft's form (`…&upstream=pyyaml`) suppresses it in Syft→Grype but not in Trivy→Trivy. A supplier who copies the PURL from its own Syft SBOM writes a statement that consumers with a Trivy SBOM cannot apply.

**Rules observed in both scanners:**

1. **Vulnerability ID.** The statement's name or one of its aliases must equal the ID the scanner gives the finding. Grype uses the GHSA ID for PyPI findings (and the CVE for Ubuntu findings); Trivy uses the CVE. Neither uses its own CVE↔GHSA link, so a statement needs both IDs to be applied by both scanners.
2. **Product.** PURL type, namespace and name must be equal. If the statement has a version, it must be equal, with no ranges (`5.3.1` does not match `5.3.1+acme1`); without a version it matches every version. Every qualifier in the statement must be on the component with the same value; qualifiers that only the component has are ignored.
3. **Reach.** A statement whose product is a package applies to that package in every SBOM it is applied to. local-backport's statement stays in its image only because the rebuild has its own version, `+acme1`. A backport that kept `5.3.1` could only be covered by a statement that also covers upstream 5.3.1, as (b) shows.

## 5. Mapping to CISA (findings in §4)

- **"[product_id] and [subcomponent_id] SHOULD reference existing SBOM identifiers"** (Minimum Requirements §2.5). §4.1, §4.2 and the qualifier probes in §4.5 show that the "existing SBOM identifier" depends on which tool wrote the SBOM, and that scanners match on those details. The supplier's correct deb PURL misses Syft's PyPI duplicate, and Syft's form of the deb PURL is not applied to Trivy's SBOM.
- **"correlation against existing inventories [is] difficult … as long as there is a lack of consensus around a global software identification system"** (When to Issue VEX). Reproduced directly by §4.1–§4.3.
- **"VEX consumers should … deconflict VEX information for multiple occurrences of the same upstream component"** (When to Issue VEX). CISA means one upstream component reached through several supply-chain paths. The Syft duplicate is a related but different case: one installed package recorded twice in one SBOM, which a consumer has to deconflict in the same way.
- **Tools "should sufficiently validate the accuracy of VEX information"** (When to Issue VEX). The product-blind post-filter in §4.4 applies statements about other packages.
- **Backport: `fixed` vs `vulnerable_code_not_present`.** Scanners treat both the same. The evidence (code identical to 6.0.2, produced by a patch) fits CISA's `fixed` ("contain fixes for [vul_id]") better than vcnp, whose CISA examples are code that was stripped or never added.

## Limits / next steps

- **SBOM format.** §3 uses CycloneDX only. The §4.1 probe shows that the deb-patched FP from Syft→Grype disappears with Syft JSON or SPDX, but format is not yet a factor of the matrix (#1).
- **Package as product.** The supplier VEX uses the package as the product. A VEX scoped to the image (image as product, package as subcomponent, as CISA frames it) can't be tested here, because neither SBOM gives the image root a PURL. Pushing the images to a local registry would give them digests and allow that test (#2).
- **`affected` statements** cannot change a scan's output, so "is the VEX applied?" is tested only on the three non-vulnerable variants and in the probes.
- **Base image.** Ubuntu 20.04 is past standard support (Trivy warns about it; Grype uses the ESM channel). That is fine for this 2020 CVE, but newer advisories may be handled differently.
- One CVE, one ecosystem, one version of each tool. Results are from 2026-10-08.
- Not yet run: cve-bin-tool and Dependency-Track (CycloneDX VEX path).
