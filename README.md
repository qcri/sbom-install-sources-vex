# Same library, eight installs: what SBOMs, scanners and VEX miss

Part of the [Agentic AI Security](https://cs.qcri.org/agentic_-ai_security/) research project at QCRI.

**Question.** Install the same vulnerable library (PyYAML 5.3.1, CVE-2020-14343) in different ways: Ubuntu apt, PyPI, git, a local source tree, a local backport (a 5.3.1 rebuild with the fix patched in), and a local relabel (the unchanged 5.3.1 code rebuilt as version 6.0.2). Then ask three things:
1. Does each SBOM generator identify the component correctly?
2. Does each scanner report the vulnerability correctly?
3. Does a correct supplier VEX statement actually get applied?

**Short answer.** Not reliably. Which SBOM generator and scanner are paired, how the library was installed, and the exact PURL decide the outcome more than the code does. The details are in **[RESULTS.md](RESULTS.md)**. The article **[How the SBOM Decides What VEX Can Fix](article/article.md)** tells the same story for a wider audience; it is also published as a [blog post](https://mohannadcse.github.io/blog/2026/sbom-decides-what-vex-can-fix/).

## Design

```
SUPPLIER ("Example PSIRT")                      CONSUMER
 build image ─► SBOM (Syft | Trivy) ─────────────► SBOM ─┐
      └─► oracle.py (PoC in the container) ─► VEX ─► VEX ─┴─► scanner (Grype | Trivy) ─► findings
                                     (vexctl create)            --vex  or  vexctl filter on SARIF
```

- **8 images, all `ubuntu:20.04` / Python 3.8.10.** Only the install method differs:

  | variant | install |
  |---|---|
  | deb-unpatched | `apt install python3-yaml=5.3.1-1` |
  | deb-patched | `apt install python3-yaml=5.3.1-1ubuntu0.1` (Ubuntu security fix) |
  | pypi | `pip install PyYAML==5.3.1` |
  | git | `pip install git+https://github.com/yaml/pyyaml.git@5.3.1` |
  | local | `pip install ./pyyaml-5.3.1` |
  | local-backport | same tree + Ubuntu's CVE patch, rebuilt as version `5.3.1+acme1`: a backported fix ([RESULTS.md](RESULTS.md#setup)) |
  | local-relabel | same unmodified tree, rebuilt as version `6.0.2`: vulnerable code with a fixed version label ([RESULTS.md](RESULTS.md#setup)) |
  | pypi-fixed | `pip install PyYAML==6.0.2` (control) |
- **Ground truth** is `app/oracle.py`. It runs the public PoC with a harmless payload inside each container, so it never relies on a scanner.
- **VEX** is written as the supplier would write it (`vexctl create`): the status comes from the oracle, and the product is the PURL the supplier knows it shipped.
- **Tools**, all pinned (commands in [RESULTS.md](RESULTS.md#pipeline-tools-and-commands)):
  - **SBOM generators:** Syft 1.54.1 and Trivy 0.75.0. They read each built image, saved as an archive file, and list the packages installed in it as CycloneDX. They do not read the source code or manifests such as `requirements.txt`.
  - **Scanners:** Grype 0.120.1 and Trivy 0.75.0, each reading both generators' SBOMs and matching them against its own vulnerability database. "Syft→Grype" means an SBOM generated by Syft and scanned by Grype.
  - **VEX:** vexctl 0.4.4 writes the supplier's OpenVEX statement (`vexctl create`). The statement is applied in two ways: inside the scanner (`--vex`), or after the scan by a post-filter, `vexctl filter`, which removes results from the scanner's SARIF report.

### Design decisions

- **One base image for all variants.** Ubuntu 20.04 is the only release that ships both the unpatched (`5.3.1-1`) and the patched (`5.3.1-1ubuntu0.1`) `python3-yaml`, so every variant uses it and the install method is the only difference that matters for this CVE. (The libyaml C extension also differs; it is not involved.) PyYAML 5.3.1 also builds and is exploitable on Python 3.10–3.13, if the pip variants ever need a newer base.
- **The oracle decides the truth, never a scanner.** Each VEX status is taken from it, so every statement is correct by construction, and the experiment measures only whether the statement is *applied*.
- **local-backport uses Ubuntu's own patch.** Its `constructor.py` is then byte-identical to the patched deb's and to 6.0.2's, which leaves packaging and identity as the only variables.
- **local-relabel changes only the version in `setup.py`.** The code, `yaml.__version__` included, stays 5.3.1, so the declared version is its only difference from local: the hypothesis tested in the direction opposite to local-backport.
- **The backport gets both `fixed` and `not_affected` (`vulnerable_code_not_present`).** The scanners treat them the same; `fixed` fits CISA's definitions better ([RESULTS.md §5](RESULTS.md#5-mapping-to-cisa-findings-in-4)).
- **Pinned tools, frozen databases.** Syft, Grype, Trivy and the base image are pinned by digest. The vulnerability databases are downloaded on first use and then frozen: `GRYPE_DB_AUTO_UPDATE=false` and `GRYPE_DB_VALIDATE_AGE=false` for Grype, `--skip-db-update` for Trivy.

## Headline results

1. **A patched Ubuntu deb gets a false positive through Syft's CycloneDX SBOM.** Syft lists the deb and, separately, the Python metadata inside it, as `pkg:pypi/pyyaml@5.3.1`. That metadata keeps the upstream version, so Ubuntu's fix (`-1ubuntu0.1`) is invisible and both scanners match it against the PyPI advisory (`< 5.4`). In its own JSON and in SPDX, Syft marks the PyPI entry as owned by the deb, and Grype then drops it; the CycloneDX output loses that link. The supplier's correct deb VEX can't reach the finding.
2. **Each scanner reads the deb's source package only from its own vendor's fields.** Ubuntu files the CVE under the source package `pyyaml`, not the binary package `python3-yaml`.
   - Grype reads it from Syft's PURL qualifier `upstream=pyyaml` or property `syft:metadata:source`.
   - Trivy reads it from its own property `aquasecurity:trivy:SrcName`.

   So a Trivy SBOM fed to Grype misses the vulnerable deb (false negative), and a Syft SBOM fed to Trivy misses the deb component (it is reported only through the PyPI duplicate). This also holds with SPDX.
3. **The PURL drops the install origin.** pypi, git and local installs all become `pkg:pypi/pyyaml@5.3.1`, except that Syft adds `vcs_url` for git. Syft keeps the git and local origin in `externalReferences`; Trivy keeps neither. Matching and VEX use the PURL.
4. **`--vex` applies a statement when its product PURL and vulnerability ID match a finding, and both checks have sharp edges.**
   - A statement whose product has no version, or has upstream's version (what a backport that kept `5.3.1` would need), also suppresses the real vulnerability in other images. The backport here stays contained only because its rebuild carries its own version, `+acme1`.
   - A statement must list the ID each scanner uses: Grype keys this PyPI finding by its GHSA ID, Trivy by the CVE.
   - Qualifiers in the statement's PURL must be on the component: a deb PURL copied from a Syft SBOM (`…&upstream=pyyaml`) is not applied to a Trivy SBOM.
5. **`vexctl filter` on SARIF ignores the product.** It removes every finding whose ID has a `fixed` or `not_affected` statement: a statement about an unrelated npm package removed a real PyYAML finding.
6. **Ubuntu's patched `constructor.py` is byte-for-byte identical to PyYAML 6.0.2's**, yet its Python metadata still says `5.3.1`.
7. **Vulnerable code with a fixed version label is missed by every SBOM→scanner pair.** local-relabel is the unmodified 5.3.1 tree with only its version set to `6.0.2`; the exploit still works. Both SBOMs list `pkg:pypi/pyyaml@6.0.2`, the same PURL as the fixed control, and neither mentions 5.3.1 or the vulnerable file's hash. All four pairs report nothing (FN), with or without VEX: the supplier's `affected` statement cannot add a finding. This is local-backport in reverse.

Against the oracle, 11 of the 32 SBOM→scanner results are wrong without VEX, 7 with `--vex`, and 8 with `vexctl filter`. The 7 left after `--vex` are 3 deb cases (results 1–2) and the 4 local-relabel misses (result 7).

## Run it

Requirements:
- Linux with `podman`, `curl` and `patch` (Docker is not supported yet: #3);
- Python 3.12+, or 3.10.12+ / 3.11.4+ (it needs `tarfile` extraction filters), on the host, only to drive the script;
- network access on the first run. That run also downloads the Grype and Trivy vulnerability DBs (about 5 GB) into `.cache/`; later runs reuse them unchanged.

```bash
python3 -I run.py                    # everything: fetch build evidence sbom vex scan report probe
podman run -it vexlab/git:1.0 bash   # inspect any variant; /app/evidence.sh prints what we collect

# or just look at the reported run without rebuilding (from the repository root):
tar -xJf out/scans-2026-10-08.tar.xz && tar -xJf out/scans-2026-11-05-local-relabel.tar.xz && python3 -I run.py report
python3 -I tools/validate.py         # independent check: recompute every row from the raw scans
```

Notes:
- **Containers run one at a time.** podman containers that share a `:Z` volume race on SELinux relabelling when run in parallel, and Trivy then fails with `mkdir /root/.cache/trivy/fanal: permission denied`.
- **The databases are frozen after the first download.** Delete `.cache/grype` or `.cache/trivy` to get newer ones; `run.py` never updates them. Grype refuses a database older than 5 days by default, so `run.py` sets `GRYPE_DB_VALIDATE_AGE=false`.
- **`run.py` stops at the first failing container** and prints its stderr.
- **The image archives in `out/images/` are about 1 GB** (git-ignored). `run.py build` recreates them; `probe` needs the two deb images.
- **The venvs upgrade pip to 25.0.1**, the last version for Python 3.8. Ubuntu 20.04's pip 20.0.2 predates `direct_url.json`, so git and local installs would otherwise leave no trace of where they came from.
- **Ubuntu 20.04 is in ESM.** Grype logs `using channel "esm"`, and Trivy warns that the OS version is no longer supported. The release-pocket package `5.3.1-1` is still installable by pinning its version.

## Provenance

- **Reported run: 2026-10-08**, seven variants. The committed `out/` is a snapshot of it; the raw scans are in `out/scans-2026-10-08.tar.xz`.
- **Review: 2026-10-13.** Re-scanning every committed SBOM with the pinned tools and the databases of 2026-10-13 reproduced all 32 rows of that run: 28 verdicts, plus the second local-backport statement in 4 pairs. Ground truth was re-checked against PyPI's and Ubuntu's own packages, and the probes in `out/probe/` were generated that day.
- **local-relabel: added 2026-11-05**, built and scanned with the pinned tools and the databases of 2026-10-13; the frozen 2026-10-08 databases were no longer available on that host. Re-scanning the other seven variants' SBOMs with the same databases reproduced all 32 rows. That host had Docker but not podman, so `run.py` ran through a podman-to-docker shim. Its raw scans are in `out/scans-2026-11-05-local-relabel.tar.xz`; `out/probe/` was not re-run.
- Tool, database and base-image versions: `out/versions.txt`.

## Open questions

Tracked as issues:
- #1: make the SBOM format (Syft JSON, SPDX, a direct image scan) a factor of the matrix;
- #2: is VEX leakage fundamental? Test image-scoped VEX and a backport that keeps `5.3.1`;
- #3: Docker support, and provenance generated by `run.py`;
- #4: report errors by mechanism, not only as a count;
- #5: which findings to report upstream.

Not tracked yet:
- **More consumers and VEX formats:** cve-bin-tool, OWASP Dependency-Track, and Trivy with CSAF and CycloneDX VEX.
- **Distro-published VEX:** compare Canonical's OpenVEX statement for `python3-yaml` with ours. Its feed (`security-metadata.canonical.com/vex/`) returned 503 on 2026-10-08.
- **Runtime SBOMs:** memory-based tools record the import name `yaml`. Does `pkg:pypi/yaml@5.3.1` match any advisory?
- **Generalise:** repeat with a second ecosystem (npm or Go) and a second CVE, to see which findings are specific to PyYAML.

## Layout

```
run.py                   whole pipeline, one function per stage
tools/validate.py        independent re-parse of the raw scans, checked against out/results.json and out/tables.md
app/                     app.py (product), oracle.py (ground truth), evidence.{sh,py}
variants/<name>/         one Containerfile per install method
src/patches/             Ubuntu's CVE-2020-14343.patch (= upstream commit 7adc0db)
out/<variant>/           evidence.txt, sbom.{syft,trivy}.cdx.json, *.openvex.json
out/tables.md            identity table and the full verdict matrix;  out/results.json
out/probe/               root-cause probes (probes.txt) and VEX-matching probes
out/scans-2026-10-08.tar.xz   raw scanner JSON + SARIF of the reported run
out/scans-2026-11-05-local-relabel.tar.xz   the same for local-relabel, added 2026-11-05
out/versions.txt         tool, vulnerability-DB and base-image versions
article/                 the article and its figures (figures/src/make_figures.py draws them)
```
